# FreeDcam → SAF / minSdk30 / de-googled fork — migration notes

Base: KillerInk/FreeDcam @ commit see `git log -1`. GPLv2.

## Target spec
- SAF-only storage, no legacy WRITE/READ_EXTERNAL_STORAGE
- local-first (no cloud; existing local-Wi-Fi remote-camera + geotagging kept)
- de-googled (no GMS/Firebase/Play — none were present; Hilt/Dagger being removed too)
- minSdk 30 (Android 11+), targetSdk 36 (already was)
- unrooted device, sideload only, personal use
- Windows 11 / Android Studio / JDK 21 / Kotlin+Java (no TS)

### Build tooling downgrade (AGP 9.0.0 -> 8.12.1, Gradle 9.1.0 -> 8.14.3)
Not part of the original spec, and not something I'd flagged in earlier drafts of these notes - here's what it actually is, checked against current AGP/Gradle documentation and real-world reports rather than left as a mystery:

- AGP 9.0 (shipped Jan 2026, which is what upstream was already on) is a genuinely severe breaking release, not a routine bump: Kotlin support is now built into AGP itself, so explicitly applying the `org.jetbrains.kotlin.android` plugin - which upstream's `kotlin.compose` plugin alias pulled in as a transitive dependency - now causes a hard build failure, not a warning. AGP 9.0 also drops `wearApp{}`, `splits.density{}`, and the legacy Instant Apps plugin outright, with no opt-out.
- Upgrading AGP from 8.x to 9.x carries a hard, non-optional requirement to upgrade Gradle to 9.x alongside it - there's no supported way to pair AGP 9.x with an 8.x Gradle wrapper. That's why this downgrade touched both version numbers together rather than just one.
- As of a March 2026 developer report, IntelliJ/Android Studio's own plugin tooling hadn't yet caught up to AGP 9's changes and didn't support any AGP version past 8.12 for a while, which is a real, independently-reported reason projects were deliberately staying on the AGP 8.12.x/8.13.x line during this period.
- AGP 10.0 / Gradle 10.0 (which would force the *next* wave of these removals) have **not shipped as of this writing** - still described as a mid/second-half-2026 target everywhere I can find. So this wasn't "avoid 10.0 because 9.x stopped being available" (9.x is alive and still being actively released); it reads as a retreat off an already-disruptive AGP 9.0 back to the last well-understood, tooling-compatible 8.x line, most plausibly to sidestep the built-in-Kotlin conflict and the DSL/Variant API migration work in one move, without touching any of that in an already-large changeset.
- One regression worth fixing regardless of the above: the Gradle wrapper's `distributionSha256Sum` integrity pin got removed as part of this same change (`gradle-wrapper.properties`). That checksum is what protects the wrapper download against a compromised or MITM'd Gradle distribution; it should be restored for whichever Gradle version the project ends up on (get the correct hash from `https://gradle.org/release-checksums/` for 8.14.3, or whatever version is current when this gets picked back up).

### Correction: `ScreenSlideFragment`'s delete button lost its `GetWriteExternal()` gate
Found during a later full code review, not during the original migration work. `ScreenSlideFragment.onDeleteButtonClick` originally branched on `!settingsManager.GetWriteExternal()` (show the delete dialog directly - no SAF folder needed) vs. the `SDK_INT > P` SAF-folder-picker path. When the dead SDK_INT wrapper got removed per this stage's stated plan, the `GetWriteExternal()` condition was accidentally dropped along with it, not just the dead branch around it - every version of this file everywhere else in the migration correctly kept `GetWriteExternal()` as the real gate. The result: tapping delete unconditionally required a SAF folder to already be picked, even for a plain MediaStore-backed photo (`UriHolder.delete()` only ever calls `ContentResolver.delete(...)`, no SAF folder involved) - meaning anyone using the MediaStore fallback this same stage's note above says is fully supported ("used until a folder is picked") could no longer delete anything from the viewer. Fixed by restoring the `GetWriteExternal()` check alongside the (still dead, still correctly removed) SDK_INT branch.

Note on scope: I kept the MediaStore fallback (used when the person hasn't picked a SAF folder yet) rather than making SAF strictly mandatory. It requires no permission, isn't legacy storage, and removing it would mean no photo can be saved before the person visits settings and picks a folder. Say the word if you'd rather force the SAF picker on first launch instead.

## Stage 5 — Physical camera selection — DONE
New feature, not part of the original spec: pin capture+preview to one physical sensor of a logical multi-camera instead of the vendor's automatic lens fusion.

- [x] `SettingKeys.PHYSICAL_CAMERA_ID` - new setting key, follows the exact pattern of the existing `SECONDARY_SENSOR_SIZE` key.
- [x] `PhysicalCameraDetector` (new, `featuredetector/camera2/`) - checks `CameraCharacteristics.getPhysicalCameraIds()`; only marks the setting supported when there are 2+ physical sensors (true logical multi-camera). Labels each as `"<id> (<focal length>mm)"` rather than guessing at "ultrawide"/"tele" names, since those mean different things across vendors - this app already prefers showing real numbers over friendly-but-fake labels everywhere else (ISO, f-number, shutter speed), so this matches that.
- [x] Registered in `Camera2FeatureDetectorTask` right after `PictureSizeDetector`.
- [x] `PhysicalCameraModeApi2` (new, `camera2/parameters/modes/`) - the selectable parameter, follows `SecondarySensorSizeModeApi2`'s exact shape (a `BaseModeApi2` subclass using `CameraThreadHandler.restartPreviewAsync()` to force a session rebuid on change, same as `PictureSizeModeApi2` does for size changes).
- [x] Registered in `ParameterHandlerApi2`, gated on `isSupported()` like every other conditional parameter in that file.
- [x] Wired into `SettingGroupConfig` (the NextGen theme - the only UI theme this app has, as of the classic-theme correction described below), in the picture group next to `SECONDARY_SENSOR_SIZE`/`PICTURE_SIZE`. (Originally also wired into `SettingsMenuItemFactory` for the classic left/right-menu theme; that theme was removed entirely in a later pass, so there's now only one theme to wire this into - see the correction section below.)
- [x] `CaptureSessionHandler`: added `physicalCameraId` field + `SetPhysicalCameraId()`. `CreateCaptureSession()` (both overloads - covers stills via PictureModuleApi2/RawZslModuleApi2 *and* video via VideoModuleApi2) now builds `OutputConfiguration`s via a shared `buildOutputConfigurations()` helper instead of the old plain-`Surface`-list `createCaptureSession()` call, since only the OutputConfiguration-based session APIs support `setPhysicalCameraId()`. Switched to the officially-public `createCaptureSessionByOutputConfigurations` (API 24+), not the hidden reflection-based `createCustomCaptureSession` this file uses elsewhere for vendor OPMODE - this didn't need that, so it isn't using it. `physicalCameraId == null` (the "Auto" choice) behaves identically to before - every OutputConfiguration is unpinned, same as the old plain-Surface path.

Scope decisions worth knowing about:
- High-speed sessions (`CreateHighSpeedCaptureSession`) and the vendor custom-OPMODE session path are untouched - physical camera selection isn't offered while either of those is active. Both are narrower, already-vendor-specific paths; forcing physical-camera pinning through them felt like a good way to introduce a subtle bug I couldn't verify without hardware.
- If a chosen physical stream/format combination isn't actually valid for a given surface on some device, `setPhysicalCameraId()` throws - I catch that per-surface and silently fall back to the unpinned (logical) stream for that surface rather than failing the whole session. Worth watching for in Logcat on first test.

## Testing this specifically
Needs a logical multi-camera phone (most midrange-and-up phones from the last several years qualify) - on a single-lens phone the setting simply won't appear, which is the correct/expected behaviour. Look for "Physical Camera" in the picture settings group; switching away from "Auto" should visibly change field of view in preview immediately (session rebuild via restartPreviewAsync). If the picker doesn't appear on a phone you know has multiple lenses, check Logcat for `PhysicalCameraDetector` - some vendors still don't mark their extra lenses as part of a single logical multi-camera even though 2+ are present, in which case there's nothing this API can see.

## Stage 6 — Focus stacking — DONE
New feature. Turned out to need far less new capture machinery than expected: this codebase already had `AfBracketApi2`, a module that bursts a capture across a `LENS_FOCUS_DISTANCE` range - which is exactly the capture side of focus stacking. So this feature is really just "add a local merge step after an existing bracket finishes," not a new capture pipeline.

- [x] `freed.imaging.FocusStackProcessor` (new package) - the actual merge. Reads back the N already-saved JPEG frames via `BaseHolder.getInputStream()` (works identically whether the frames live in a SAF folder or MediaStore - same abstraction the SAF migration stage relied on), tiles the image (128x128), decodes each tile from every source via `BitmapRegionDecoder` (never holds more than one tile per source in memory - N full-resolution bitmaps at once would risk OOM), scores each tile with a cheap gradient-based sharpness proxy, keeps the sharpest, and composites into one output bitmap. Saves the result through `FileListController.getNewImgFileHolder()` - the same SAF/MediaStore-aware path every other capture mode uses - and calls `addFromEventFile()` so it shows up in the gallery immediately, no restart needed.
- [x] `AfBracketApi2` overrides `fireOnWorkFinish(BaseHolder[] files)` - the existing hook that already only fires once every frame in the burst has actually finished its async save (not just been captured - this codebase already tracks that correctly via `BurstCounter`), so there's no race condition to worry about. Calls `super` first (bracket frames are always saved normally), then kicks off the merge in the background if the new toggle is on.
- [x] `SettingKeys.FOCUS_STACK_MERGE` - a plain global boolean (`GlobalBooleanSettingMode`, same kind as the existing `PLAY_SHUTTER_SOUND`), not a per-device-capability parameter - the merge is pure software, so unlike physical camera selection there's no detector needed and no `ParameterHandlerApi2` registration; it's just read directly wherever needed, exactly like `PLAY_SHUTTER_SOUND` already is. Defaults to off. Wired into the NextGen theme (the only theme this app has - see the correction section below) right next to the shutter-sound toggle.
- [x] While in `MediaStoreController` for this (`FocusStackProcessor` calls into it via `FileListController`), found and removed two more `SDK_INT <= P` dead branches (`getUri()`/`getVideoUri()`'s legacy `VOLUME_EXTERNAL` selection, and `addImg()`/`addMovie()`'s legacy `MediaStore.Images.Media.DATA` write) - same always-false-at-minSdk-30 class of dead code as the Stage 2/3 storage cleanup, directly adjacent to code this feature now depends on, so worth fixing while there.

Explicit scope decisions:
- **JPEG only.** `BitmapRegionDecoder` doesn't understand RAW/DNG. If `PICTURE_FORMAT` isn't JPEG or Jpg+DNG when a bracket finishes, the merge is silently skipped (logged, not a crash) and the bracket frames are still saved normally - developing N DNGs through the LibRaw JNI pipeline before stacking would be a substantially bigger feature and a separate task.
- **No alignment pass.** Assumes a static scene (tripod/macro rig) - hard tile boundaries, no feathering, no motion compensation. This matches what most phone focus-stacking tools do for a first version; handheld tolerance would be a real v2.
- Decoupled from the live capture/save pipeline on purpose - it only reads files that have already finished saving through the existing path, and writes exactly one new file through the existing path. Nothing about `CaptureController`/`ImageTask`/the code every other capture mode depends on was touched.

### Testing this specifically (focus stacking)
Turn on "Merge Af-Bracket into Focus Stack" in settings, set picture format to Jpeg, switch to the Af-Bracket module, and shoot something with visible near-to-far depth (a macro subject is the clearest test) on a tripod. You should get the usual N bracket frames in the gallery, plus one `focusstack_*.jpg` a few seconds later with more of the frame in focus than any single source frame. Check Logcat for `FocusStackProcessor`/ `AfBracketApi2` if the merged file doesn't appear - most likely causes are the format check skipping it (confirm Jpeg, not RAW) or a frame-size mismatch (shouldn't happen within one bracket run, but the processor aborts cleanly and logs why rather than producing a corrupt output if it does).

## Building on Windows 11
1. Install Android Studio (current stable channel).
2. Install JDK 21 - either via Android Studio's bundled JBR (Settings > Build Tools > Gradle > Gradle JDK, pick 21) or a standalone Temurin 21, then point `JAVA_HOME`/Gradle's JDK setting at it.
3. Open the project folder in Android Studio, let it sync. It will prompt to install:
   - Android SDK Platform 36 (compileSdk/targetSdk)
   - NDK 27.3.13750724 (pinned as `ndkVersion` in app/build.gradle - the caveat below is resolved, Stage 9)
   - CMake (for the native LibRaw/libtiff build)
4. Build > Make Project, or `gradlew.bat assembleDebug` from a terminal in the project root. For the round
   workflow use `python tools/critique/walk.py build` (arm64-v8a only, runs `tools/spec_check.py` first; SPEC.md §2).
5. Enable Developer Options + USB debugging on the phone, plug in, Run.
6. Signing: the tree has no keystore and no `signingConfig` (corrected 2026-09-28 - an earlier line here said
   upstream's `key/freedcamkey.jks` was checked in; it is not), so debug builds are signed with the standard
   Android debug key. Fine for personal sideloading.

Known caveat: `ndkVersion` is now 27.3.13750724 (see "Build tooling downgrade" under Stage 1) rather than the 21.1.6352462 an earlier draft of these notes described - I still haven't been able to verify this resolves cleanly and builds through the CMake config in an actual Android Studio session, since I have no Android SDK/NDK in this sandbox. The CMake config doesn't reference anything NDK-r21-specific, so this should be a non-issue, but it's untested by me either way - flag it here if Android Studio's SDK Manager has trouble with it.

Related fix, verified during a later full code review rather than caught during the original migration work: `jni/LibRaw/swab.cpp`/`swab.h` now guard the project's own `swab()` declaration and definition behind `#if !defined(__ANDROID__) || (defined(__ANDROID_API__) && __ANDROID_API__ < 28)`. This is a real, necessary consequence of the minSdk 21 -> 30 bump above, not a cosmetic change: bionic's `unistd.h` has declared `swab()` (with C linkage) since API 28, and bumping minSdk past that threshold means `__ANDROID_API__` for this build now exceeds 28 for the first time, which would otherwise produce a genuine "declaration has a different language linkage" conflict between bionic's declaration and this project's own unguarded one. `swab.cpp` also now `#include`s `swab.h` (it didn't before), so the guard actually keeps the declaration and definition in sync instead of relying on them happening to match. Confirmed correct by inspection; still worth an eye during the first real NDK build, same as the `ndkVersion` caveat above, since nothing here has actually been compiled.

Note: the upstream repo pulls `renderscript-intrinsics-replacement-toolkit` in as a git submodule. Since this archive isn't a git checkout, that folder's contents are just copied in directly instead - if you set this up as its own git repo, add it back as a submodule (or plain vendored copy) rather than an empty folder.

## Stage 8 — vendored native library CVEs (LibRaw/libtiff) — PARTIAL, one fix applied, library swap not started
Flagged in an earlier session while in the native build code for unrelated reasons, then followed up on request. This app parses untrusted RAW/TIFF files handed to it by camera hardware (and by whatever remote-camera peer or SD card content reaches it) through vendored C sources in `app/src/main/jni/LibRaw` and `app/src/main/jni/tiff`, so the attack surface here is "a file the app didn't choose, run through native code" - a materially more consequential category of bug than the build-cleanup work these notes otherwise track.

Versions confirmed by reading the vendored version headers: LibRaw 0.19.1 (`libraw_version.h`, released late 2018) and libtiff 4.0.9 (`RELEASE-DATE` file, `20171118`). Both are roughly 8 years old as of this writing.

Public CVE history for these exact versions, found by search rather than assumed: libtiff 4.0.9 has a long trail of fixes landing the following year and after, mostly NULL-deref/DoS crashes on crafted TIFF input (CVE-2018-5784, -17795, -18557, -18661, -19210, plus the 2018-17000/17100/17101 cluster) and one out-of-bounds write via JBIG decoding, none of which are present in this tree. LibRaw 0.19.1 is worse: two NULL-pointer-dereference CVEs are filed against 0.19.1 by name (`LibRaw::copy_bayer`, `LibRaw::raw2image`), and the fixes for a stack buffer overflow (`identify_process_dng_fields`), a heap buffer overflow (`raw2image`), a missing thumbnail size range check, and an out-of-bounds write in EXIF/GPS parsing all landed in the 0.20.x/0.21.x line, years after this snapshot. The bug class hasn't stopped either - Cisco Talos and Debian LTS disclosed six more LibRaw heap-overflow/integer-overflow CVEs in 2026 alone (CVE-2026-20884, -20889, -21413, -24660, -5342, -24660), meaning even a from-scratch upgrade needs to land on the current patch level, not just "any 0.21.x."

Diff pass against pristine upstream, done to find out what local changes would need to survive a library swap before recommending one: downloaded the real upstream `LibRaw` tag `0.19.1` from `github.com/LibRaw/LibRaw` and the real upstream libtiff `Release-v4-0-9` tag from the `vadz/libtiff` GitHub mirror (verified its `RELEASE-DATE` file matches the vendored copy's `20171118` exactly before trusting it as a baseline), then diffed both trees against the vendored copies with line-ending normalization (the vendored copies are LF, upstream ships CRLF, which otherwise makes every file look changed when it isn't).

LibRaw result: essentially untouched. The only real content differences across the whole tree are two one-line `#include <swab.h>` additions (`internal/dcraw_common.cpp`, `src/libraw_cxx.cpp`) for a project-local `swab()` shim the NDK doesn't provide - a trivial, well-understood portability addition already covered by the API-28 linkage guard noted under "Building on Windows 11" above. A from-scratch swap to a current LibRaw release should be low-risk for this reason: there's almost nothing local to re-port.

libtiff result: genuinely modified, and worth reading closely before assuming a drop-in upgrade is simple.
- GPS IFD tag support was added wholesale and isn't in upstream 4.0.9 at all: `GPSTAG_*` definitions and a `gpsFields`/`gpsFieldArray` table in `tif_dirinfo.c`, a new `tfiatGps` enum value and `_TIFFGetGPSFields()` declaration in `tif_dir.h`, the `TIFFCreateGPSDirectory()` function and its call-through in `tif_dir.c`, and its public declaration in `tiffio.h`. This is almost certainly what backs the "existing local-Wi-Fi remote-camera + geotagging kept" line in this file's own Target spec above - losing it in a careless swap would silently break geotagging, not just add old-CVE risk.
- The DNG/EXIF tag table in `tif_dirinfo.c` and `tiff.h` was also hand-expanded with roughly a dozen additional tags upstream 4.0.9 doesn't define (`OpcodeList2`/`3`, `ProfileToneCurve`, `NoiseProfile`, `BaselineExposureOffset`, `ForwardMatrix1`/`2`, standard EXIF tags like `ExposureTime`/`FNumber`/`ApertureValue`/`ISOSpeedRatings`/`Flash`/`FocalLength`, `TIFFTAG_EP_STANDARD_ID`), likely backported from a newer libtiff or the Adobe DNG SDK to widen DNG metadata support.
- `tif_unix.c` gained Android logcat output (`__android_log_print` calls tagged `freedcam.libtiff`) on the two warning/error paths - purely diagnostic, no behavior change.
- Two `if (v32 % 16)` tile-size validation blocks in `tif_dir.c` are commented out. These sit in `TIFFVSetField` under `TIFFTAG_TILEWIDTH`/`TIFFTAG_TILELENGTH` - the tag-*write* path, exercised when this app itself writes a DNG, not when it parses an incoming file - so this doesn't touch the untrusted-input attack surface flagged above. Worth understanding why it was disabled before restoring it, but not urgent.
- One `TIFFTAG_ACTIVEAREA` field definition in `tif_dirinfo.c` is commented out, meaning that tag currently isn't recognized as a DNG field at all. Not obviously security-relevant either way, but a real behavior difference from upstream worth knowing about if any DNG output ever needs that tag.
- **The one finding here that actually matters on its own, independent of "the library is old":** in `tif_dirinfo.c`, `_TIFFCreateAnonField()` - the function that builds a placeholder `TIFFField` whenever the *read* path (`tif_dirread.c`) encounters a tag ID it doesn't recognize in an incoming file - allocates a 32-byte `field_name` buffer but has its one-line initializer commented out: `//(void) snprintf(fld->field_name, 32, "Tag %d", (int) tag);`. That buffer is then used directly as a `%s` argument in multiple `TIFFReadDirEntryOutputErr`/`TIFFWarningExt` calls in `tif_dirread.c`, all on the untrusted-parse path, specifically for the case of an unrecognized tag. With the initializer disabled, `field_name` is allocated-but-uninitialized heap memory read as a C string whenever a crafted TIFF/DNG file carries a nonstandard tag ID - an uninitialized-memory-read bug (heap content disclosure into a log/warning string, or a crash if no NUL byte turns up within readable memory) that this fork introduced locally, on top of and separate from the ~8-year-old base CVEs above. Confirmed by reading the call sites in `tif_dirread.c`; not yet confirmed by an actual crafted-file test, since there's no NDK/build environment in this sandbox to compile and run one.

Recommended path forward, roughly in order of effort:
1. **DONE.** Cheapest, zero-risk fix, independent of everything else on this list: restored the one commented-out `snprintf()` line in `_TIFFCreateAnonField()`, `app/src/main/jni/tiff/libtiff/tif_dirinfo.c` (was line 786). Single-line change, verified against the pristine-upstream diff to be the only content difference in that file, no other lines touched. Closes the locally introduced uninitialized-read bug on the untrusted TIFF/DNG parse path without touching anything else. Not yet compiled or run against a crafted test file, since there's no NDK/build environment in this sandbox - worth exercising once this lands in a real Android Studio build.
2. Medium-term: replace the vendored LibRaw tree with a current upstream release (0.22.x as of this writing, checking for the latest patch level first) - low local-change risk per the diff above, so this should mostly be "swap the folder and rebuild."
3. Medium-term, more care needed: replace the vendored libtiff tree with a current upstream release, then re-port the GPS IFD support and the expanded DNG tag table on top of it - check first whether a current libtiff already covers some of those tags natively (`tiff.h`'s tag list has grown a lot since 4.0.9), since that could shrink the amount that actually needs re-porting.
4. Regardless of when 2/3 happen: cap LibRaw's decode memory (`max_raw_memory_mb`) and consider running RAW/TIFF parsing in an isolated process, so a memory-corruption bug in either library can't take down or pivot into the rest of the app.

Items 2-4 not started - the library swap and process-isolation work are unchanged from the original triage pass.

## Stage 7 - fatal crash on launch: JNI symbol names left behind by the package rename - FIXED

App built and installed fine but crashed on every launch, first-frame, before any UI showed:

```
java.lang.UnsatisfiedLinkError: No implementation found for java.nio.ByteBuffer glasscam.dng.CustomMatrix.init()
(tried Java_glasscam_dng_CustomMatrix_init and Java_glasscam_dng_CustomMatrix_init__)
at glasscam.dng.CustomMatrix.init(Native Method)
at glasscam.settings.SettingsManager.init(SettingsManager.java:149)
at glasscam.ActivityAbstract.onCreate(ActivityAbstract.java:101)
```

Root cause: at some point the Java package was renamed from upstream's `freed.*` to this fork's `glasscam.*` (`freed.dng` -> `glasscam.dng`, `freed.jni` -> `glasscam.jni`), which is not mentioned anywhere earlier in these notes and must predate Stage 1. JNI resolves native methods by encoding the calling class's fully-qualified name into the expected C symbol (`Java_<package>_<Class>_<method>`), and the native side never got the matching update - every `JNIEXPORT` in `app/src/main/jni/freedcam/` still used the old `Java_freed_dng_...` / `Java_freed_jni_...` symbol names. This built and linked fine (the linker doesn't check Java-side native method declarations against C symbol names, only `System.loadLibrary` at runtime does, via `dlsym`), so nothing caught the mismatch until first launch, at the very first native call the app makes.

CustomMatrix.init() is just the one that happened to run first (SettingsManager parses matrix XML during onCreate); every other native-backed class in `glasscam.dng`/`glasscam.jni` had the identical problem and would have crashed the same way the moment it was reached.

Fixed by renaming the JNI export symbols in all 9 affected files to match the current package (`Java_freed_dng_` -> `Java_glasscam_dng_`, `Java_freed_jni_` -> `Java_glasscam_jni_`): `CustomMatrix.cpp`, `DngProfile.cpp`, `DngStacker.cpp`, `ExifInfo.cpp`, `GpsInfo.cpp`, `LibRawJniWrapper.cpp`, `OpCode.cpp`, `RawToDng.cpp`, and `DngMatrixCalc.cpp` (this last one has no Java caller anywhere in the tree - `freed.jni.DngMatrixCalc`/`glasscam.jni.DngMatrixCalc` doesn't exist as a class - so it wasn't actually reachable and wasn't part of the crash, but it's the same class of bug and cheap to fix alongside the rest rather than leave a second landmine).

Checked and ruled out as not needing the same fix:
- `com.lge.media.MediaRecorderExRef` and `com.sonyericsson.cameraextension.CameraExtension` also declare native methods, but their packages were never touched by the rename (still `com.lge.*`/`com.sonyericsson.*`) and they load separate vendor-provided system libraries (`hook_jni`, `cameraextensionjni`), not `libfreedcam.so` - unrelated.
- `VideoRecorderExtra.getMethod()` (MIUI reflection helper, `loadLibrary(JniNames.LIB_NATIVE)`) - the entire native block is commented out and `JniNames` doesn't exist anywhere in the tree, so this file compiles as a no-op and was never going to run.
- No `RegisterNatives`/`JNI_OnLoad` table exists anywhere in `app/src/main/jni/` - all linkage is via the implicit `Java_...` symbol convention, so the rename above is the complete fix with nothing else to update in step.

**Not verified**: same limitation as every other stage in these notes - no compiler, NDK, or device available here, so this hasn't actually been built or run. The symbol-name diff itself is mechanical and low-risk (straight rename, no logic touched, brace-balance checked on all 9 files), but please do a clean rebuild-and-launch before trusting it.
